Truworths · MFCS integration

APEX Console Build Guide

How to rebuild the browse, create and modify screens in APEX. Covers the four operational pages; the existing React console keeps the reference material that does not belong in a database-hosted app.

The reason this is straightforward

All business logic already lives in PL/SQL. The React client only assembles the inbound document — validation, the step graph, endpoint resolution, payload construction and every MFCS call come from the database. Nothing under database/ changes. And because APEX runs inside the database, it calls the packages directly instead of marshalling JSON over HTTP, so this removes a boundary rather than adding one.

Keep the ORDS module regardless. Office and PLM call those endpoints machine-to-machine; APEX becomes a second consumer alongside the REST API, not a replacement for it.

01

The one piece of new code

Half a day

Do this before any page, because all four pages depend on it.

Today the inbound document is assembled in JavaScript (ui/src/formState.js). Rebuilding that in APEX page processes would leave two implementations to drift apart. Put it in a package instead — ui_pkg — so the document is built the same way whoever asks for it.

Package outline

create or replace package ui_pkg authid definer as
    -- Assembles the Office-shaped document from page values plus the size-curve
    -- collection. Presentation glue, but written in PL/SQL so the document that
    -- APEX submits is built by the same code path a test can exercise.
    function build_document(
        p_operation        in varchar2,
        p_source_style_ref in varchar2,
        p_style            in varchar2 default null,
        p_order_no         in varchar2 default null,
        p_department       in number,
        p_class            in number,
        p_subclass         in number,
        p_supplier         in number,
        p_colour           in varchar2,
        p_unit_cost        in number,
        p_retail_price     in number,
        p_delivery_loc     in number,
        p_collection_name  in varchar2 default 'SIZE_CURVE'
        -- ... remaining header fields
    ) return clob;
end ui_pkg;

The size curve is read from an APEX collection inside the body, using c001 for source variant ref, c002 size, c003 width, n001 quantity, c004 SKU id. Depending on APEX here is fine — this package is presentation glue by intent, and it is the only place that is.

Generate ACTION_REQUEST_ID before submitting, not inside

The page needs the id to poll status afterwards (stage 03). Generate it into a page item when the form is first rendered, and pass it through — do not let the builder invent one.

02

Shared foundations

Half a day

List of values, from data you already cache

MASTER_DATA is shaped for this: data_type, data_code, parent_code, description. Cascading LOVs fall straight out of it.

Department, then class cascading on department

-- P10_DEPARTMENT
select description as d, data_code as r
  from master_data
 where data_type = 'DEPARTMENT'
 order by data_code;

-- P10_CLASS   (Parent Item: P10_DEPARTMENT)
select description as d, data_code as r
  from master_data
 where data_type   = 'CLASS'
   and parent_code = :P10_DEPARTMENT
 order by data_code;

-- P10_SUBCLASS  (Parent Items: P10_DEPARTMENT, P10_CLASS)
select description as d, data_code as r
  from master_data
 where data_type   = 'SUBCLASS'
   and parent_code = :P10_CLASS
 order by data_code;

The same table holds CODE_<codeType> rows — 797 code types, 7,049 values loaded from the tenant. Point the fixed-value fields (order type, status, freight terms, cost basis, expense components, cancel reasons) at those rather than hard-coding them. That closes an outstanding item on its own.

Token status in the global page

Bearer tokens last an hour, and an expired one makes every operation fail in ways that look like unrelated bugs. Put it in the navigation bar where it cannot be missed. 

-- PL/SQL Dynamic Content region on page 0
declare
    l_status clob := client_pkg.token_status;
begin
    htp.p('<span class="t-Badge">token: ' ||
        apex_escape.html(json_value(l_status, '$.message')) || '</span>');
end;

Refresh it with a Dynamic Action on a 60-second timer, exactly as the React header does.

A reusable JSON viewer

Several pages need to show a CLOB of JSON. One PL/SQL Dynamic Content region, taking the CLOB from a collection, covers all of them — see the CLOB note in stage 06.

03

Page 10 — Build (create and modify)

3–4 days

The most involved page, and the one where the asynchronous decision matters.

Regions and items

RegionTypeContents
OperationStatic P10_OPERATION select list — the five operations. Drives conditional display of STYLE and ORDER_NO.
IdentityStatic Action request id (generated, read-only), source system, source style ref, source order ref, version, user, description.
MerchandiseStatic Department → class → subclass cascading; supplier, colour, origin and import country, currency, unit cost, retail price.
Size curveInteractive Grid On an APEX collection. Columns: source variant ref, size, width, quantity, SKU id (populated when browsing an existing style).
OrderStatic, conditional Dates, delivery location, exchange rate. Shown only for order operations.
ResultPL/SQL Dynamic Content Validation errors, the preview call plan, or the submitted request's live progress.

Buttons and processes

Validate — synchronous, instant, safe

declare
    l_status number;
    l_resp   clob;
begin
    api_pkg.validate_transaction(ui_pkg.build_document(...), l_status, l_resp);
    -- l_status 200 = valid; 422 = errors, l_resp.ERRORS is an array of
    -- {FIELD, CODE, MESSAGE} - every problem, not just the first
end;

Nothing is registered and nothing reaches MFCS. Wire this to a Dynamic Action so it can run freely.

Preview — the full call plan, still sending nothing

preview_pkg.preview_transaction(ui_pkg.build_document(...), l_status, l_resp);
-- l_resp.MFCS_CALLS[] = {sequence, stepCode, method, endpointPath, payload}

Render it as a report over json_table on $.MFCS_CALLS[*]. Because preview resolves through the orchestrator's own resolve_step, it cannot drift from what execution would really do.

Submit must not be a synchronous page process

A CREATE_ALL makes roughly thirteen MFCS calls, and VERIFY_PURCHASE_ORDER alone retries up to twelve times with ten-second sleeps. The internal budget is 240 seconds. A blocking page submit will exceed browser and load-balancer timeouts and leave the user staring at a dead page while the request is, in fact, succeeding.

Submit — enqueue, then poll

-- 1. Validate synchronously so a bad document fails immediately.
-- 2. Stash the document, then hand execution to a job:

dbms_scheduler.create_job(
    job_name   => 'MFCS_SUBMIT_' || :P10_ACTION_REQUEST_ID,
    job_type   => 'PLSQL_BLOCK',
    job_action => 'declare l_s number; l_r clob; begin '
               || '  api_pkg.submit_transaction(ui_pkg.stashed_document('''
               || :P10_ACTION_REQUEST_ID || '''), l_s, l_r); end;',
    enabled    => true);

Then poll on a Dynamic Action timer. This is where APEX beats the current console: the STEP table already holds live progress, so you can show the steps ticking over instead of a spinner. 

select step_sequence, step_code, step_status, last_error_message
  from step
 where action_request_id = :P10_ACTION_REQUEST_ID
 order by step_sequence;

Stop polling when request.request_status leaves IN_PROGRESS. Colour the rows by status — succeeded, failed, pending — and the screen explains itself.

04

Page 20 — Browse styles and orders

2–3 days

browse_pkg returns JSON CLOBs; json_table turns them into reports. These reads are deliberately uncached — a browse screen should show current tenant state.

Style list

select *
  from json_table(
         browse_pkg.list_styles(
             p_limit      => :P20_LIMIT,
             p_dept       => :P20_DEPT,
             p_item_level => '1'),
         '$.items[*]'
         columns (
             item        varchar2(30)  path '$.item',
             description varchar2(250) path '$.itemDescription',
             dept        number        path '$.dept',
             class       number        path '$.class',
             status      varchar2(2)   path '$.status'
         ));

Style detail, with its children

-- p_with_skus => 'Y' attaches children under resolved.skus
select *
  from json_table(
         browse_pkg.get_style(:P20_ITEM, 'Y'),
         '$.items[0].resolved.skus[*]'
         columns (
             sku    varchar2(30) path '$.item',
             diff1  varchar2(60) path '$.diff1',
             diff2  varchar2(60) path '$.diff2',
             status varchar2(2)  path '$.status'
         ));

resolved.source records whether the children came from itemDetail or the feed-scan fallback. Show it — when a list looks short, that field is the first thing worth seeing.

Always read orders with p_enrich => 'Y'

An order read does not carry the parent style behind its SKUs, nor the display size behind each line's diff. Enrichment resolves both. Without it, a browsed order loaded into the form fails validation on STYLE_REQUIRED_OR_RESOLVABLE and MAPPING_NOT_FOUND. The default is already 'Y' — do not override it.

Load into the form — the feature that makes this page worth building

A button that populates page 10 from the selected record is what turns browsing into modifying. Parse the JSON, set the page items, seed the size-curve collection from resolved.skus (or the order's enriched detail lines), then redirect. 

apex_collection.create_or_truncate_collection('SIZE_CURVE');
for r in (
    select sku, diff2, size_display
      from json_table(browse_pkg.get_order(:P20_ORDER_NO, 'Y'),
           '$.items[0].orderDetail[*]'
           columns (
               sku          varchar2(30) path '$.item',
               diff2        varchar2(60) path '$.diff2',
               size_display varchar2(60) path '$.resolved.size'
           ))
) loop
    apex_collection.add_member(
        p_collection_name => 'SIZE_CURVE',
        p_c002 => r.size_display,
        p_c004 => r.sku);
end loop;
05

Pages 30 and 40 — Activity and Master data

2 days for both

Where APEX is straightforwardly better than what we hand-built.

Activity — four Interactive Reports, drilling down

Pure table reads: REQUEST → STEP → ATTEMPT → EVENT_LOG, each filtered by the selection above it. Interactive Reports give filtering, sorting, saved views and Excel export for nothing, which is more than the React version has.

  • Resume button on a failed or partially completed request: api_pkg.resume_transaction(:P30_ID, l_status, l_resp). Background it the same way as submit — a resume can be just as long.
  • Attempt payloads are CLOBs. Show them in a modal PL/SQL region rather than a report column, and pretty-print with json_serialize(... pretty).
  • Highlight the error rows. EVENT_LOG.event_level = 'ERROR' is where diagnosis starts; a report highlight condition makes it findable.

Master data — one report and one button

select data_type, data_code, parent_code, description, source, refreshed_at
  from master_data
 order by data_type, data_code;

The refresh calls master_pkg.refresh_all(l_summary), which loads thousands of rows across many services. Background it — same reasoning as submit. Show MASTER_REFRESH underneath as the run log: per data type, its source, row count and any message.

SOURCE is worth surfacing prominently. Most foundation services on this tenant are empty publish queues, so a good deal of this data is derived from the item and order feeds rather than read directly. Anyone trusting a value should be able to see where it came from.

06

Three things that will bite

Read before starting

CLOBs do not fit in page items

APEX page item values are VARCHAR2-bound. Every interesting thing here — the built document, the preview plan, the status response, attempt payloads — is a CLOB, and several comfortably exceed the limit.

  • Move CLOBs through apex_collection clob001, never page items.
  • Render them in PL/SQL Dynamic Content regions that read the collection directly.
  • For reports, go straight from the CLOB into json_table — never via an item.

Long-running work needs jobs, not page processes

Said in stage 03 and again here because it is the decision most likely to be skipped and most expensive to retrofit. Submit, resume and master-data refresh all belong in DBMS_SCHEDULER jobs with the page polling for progress. Build it that way from the first page rather than converting later.

The document builder is the seam — keep it thin

ui_pkg should assemble a document and nothing else. The moment it starts deciding defaults, translating values or making rules, you have a second implementation of logic that already exists in validation_pkg, config_pkg and payload_pkg, and the REST and APEX paths will diverge. If a rule feels like it belongs in the form, it belongs in the database.
