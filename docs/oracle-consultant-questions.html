MFCS API Open Questions

Questions for Oracle, ordered by how much the answer would change what we build. Every claim below is something we observed on our own dev tenant, with the response text included — these are confirmations and clarifications, not guesses.

Tenant: rgbu-rex-truw-stg3-mfcs Spec 26.1.201.0 Evidence: docs/mfcs-actual-call-flow.md

Context worth stating at the top of the meeting

We have five operations running end to end against the dev tenant — style create, style modify, order create, order modify, and order line synchronisation — including failure recovery and resume. The questions below come from building that, not from reading documentation. Where we say a service behaves a certain way, we have the request and response on file.

Tier 1

Behaviour that shapes our architecture

If the meeting runs short, these four are the ones to get answered.

Is there any way to make a write that changes nothing fail, instead of returning SUCCESS?

Proven

What we see

PUT items/update          diff1 changed → {"status":"SUCCESS"} → item unchanged
PUT purchaseOrders/update details[] sent  → {"status":"SUCCESS"} → lines unchanged
PUT details/update        quantityCancelled repeated → SUCCESS → nothing cancelled

This is the single most consequential behaviour we have found. Because a successful response is not evidence that anything happened, we verify every write by reading the record back — which costs an extra call, a retry loop, and tolerance for feed lag on every operation. If there is a strict mode, a validation flag, or a response field we are ignoring, it would remove a large amount of machinery.

  • Is silent no-op the intended contract, or are these gaps?
  • Is there a response field that distinguishes "applied" from "accepted"?
  • Is read-back the pattern you would recommend, or is there something better?

Do the update services require the complete record, or should a partial payload work?

Proven

What we see — each fix revealed the next missing column

"Field must be entered.Field: STORE_ORD_MULT, ITEM: 100050355
  returned by program unit CORESVC_ITEM.PROCESS_IM."

"This column should not be null.Field: DIRECT_SHIP_IND, ITEM: 100050363,
  SUPPLIER: 700087 returned by program unit CORESVC_ITEM.PROCESS_IS."

"This column should not be null.Field: INNER_NAME, ITEM: 100050363,
  SUPPLIER: 700087 returned by program unit CORESVC_ITEM.PROCESS_IS."

The first of those was a description-only change — nothing to do with store order multiple. We discovered the required set by trial, one error at a time, and we have no way to know whether we have found all of it.

  • Is "send the whole record" the design, or are these defaulting gaps?
  • Is there a documented required-field set per update service?
  • Should we be doing read-modify-write — fetch current state, apply the change, send it back complete? That is where we would go next, and it is a significant design decision.
  • What does dataLoadingDestination actually control? We send "RMS" everywhere without a clear reason.

Why does purchaseOrders/update accept a details array it ignores?

Proven

We sent replaced items and quantities: SUCCESS, order untouched. We then sent a plain quantity change on the order's own existing lines — same items, nothing else different: SUCCESS, still untouched, minutes later. We have since moved to purchaseOrder/details/create and details/update, which work correctly. But the bulk service accepting and discarding line data cost us real time, because it reads as working.

  • Is the details array on that service deprecated, or does it need something we are not sending?
  • Is header-only the intended scope of purchaseOrders/update?

What is the consistency contract between a write and a subsequent read?

Proven

Measured on our tenant

Item/style publish feeds      a few seconds
Order detail line changes     ~30 seconds
foundation/item/{item}        HTTP 404 for a style created minutes earlier
RmsReSTServices itemDetail    returns that same style in full, immediately

Our verification loops are tuned to numbers we measured, not numbers we were given. That is fragile — if the lag characteristics differ in production or under load, our retry budgets are wrong and requests will fail that should have succeeded.

  • Is there a documented or guaranteed maximum publish lag?
  • Is there a read path that reflects committed state immediately, rather than the publish feed?
  • Do these characteristics change with production volume?
Tier 2

Bulk data access for on-premise reads

We have data-heavy custom applications that read RMS directly today. Rewriting them to be service-based is not viable, so we need a replicated read path. These answers determine that architecture entirely — they are contract questions more than technical ones.

Does our subscription include a Data Access Schema — read-only SQL access to a replica?

Unknown

This is the highest-value question in the section. If we can query RMS-shaped data directly, our existing applications keep their SQL and only their write paths change. Without it, everything downstream gets substantially harder.

  • Is it available, and what entities does it cover?
  • What are the concurrency, throughput and retention limits?
  • Is the schema RMS-shaped, or transformed?

What bulk extract mechanisms are available, and do they preserve RMS table structures?

Unknown

We need to know specifically whether Retail Data Extractor / Retail Insights gives us RMS-shaped data or a dimensional analytics model. If it is dimensional, it does not solve our problem — our applications expect RMS structures, and reshaping them is the rewrite we are trying to avoid.

  • Scheduled file extracts to OCI Object Storage — available, and at what granularity?
  • RDE / RI — RMS-shaped or dimensional?
  • Is GoldenGate against the MFCS source possible at all, or is CDC off the table for SaaS?
  • Full initial load plus incrementals — what is the supported mechanism?

Which foundation publish feeds are actually populated on our tenant?

Blocked

Returning HTTP 200 with zero rows

merchhier/*    diffid      difftype    diffgroup
supplier       store       warehouse   uda

We work around this by deriving hierarchy, differentiator and supplier values from the item and order feeds, and recording the source on every row. That is fragile and incomplete. It also tells us the REST layer cannot be our bulk replication path — a data store built on these feeds would have no hierarchy, no suppliers and no locations.

  • Is this a publishing configuration we can have enabled, or expected for this environment?
  • If enabled, do they carry full data sets or only deltas from the point of activation?
Tier 3

Service semantics we inferred and want confirmed

We have working answers for most of these. We want to know whether they are the sanctioned ones before they harden into our design.

Which services are idempotent, and which reject a repeated create?

Proven 
POST countriesOfManufacture/create   on an existing row →
"This item/supplier/manufacturing country already exists.
 ITEM: 100050398, SUPPLIER: 700087, COUNTRY: VN
 returned by program unit CORESVC_ITEM.PROCESS_ISMC."

Most services silently succeed on a repeat; this one fails. Because every operation we run sends its complete write set every time, we need to know which services tolerate that. We now route existing styles to the update variant — is that correct? A list of idempotent versus non-idempotent services would let us stop discovering this one failure at a time.

Is quantityOrdered: 0 with cancelInd the correct way to cancel an order line?

Proven

We found that quantityCancelled is cumulative-absolute: a line that already had 2 cancelled ignores a fresh quantityCancelled: 2 entirely. One of three identical cancellations silently did nothing until we understood this. We now drive quantityOrdered to zero with cancelInd: "Y" and a cancel code, which works regardless of history.

  • Is cumulative-absolute the intended semantics for quantityCancelled?
  • Is quantityOrdered: 0 the sanctioned full-line cancellation, or is there a proper mechanism?
  • We use ORCA codes S for a colour switch and B for a reduction — is that the expected usage?

What are the correct services and sequence for order cancellation, reinstatement, and pack lots?

Not yet built

These are our next three pieces of work, and the only ones where we have no evidence at all. Given what the first five operations taught us, we would rather ask than discover. Pack lots in particular we have not touched — we do not know whether it is a variation of what we have or a different model entirely.

  • Whole-order cancellation — is it purchaseOrders/delete, a status change, or line-by-line?
  • Reinstatement — reinstateInd on the line, or an order-level service? Does it work after a full cancellation?
  • Pack lots — which services, and what is the item model?

Is RmsReSTServices/.../Item/itemDetail supported, and why is it absent from the OpenAPI document?

Unknown

It is the only call that returns a style with its children in one request, and the only read that works on a style created moments earlier. We depend on it in production paths. It does not appear in the 26.1.201.0 specification we were given, which makes us nervous about its stability.

  • Is it supported, and will it survive upgrades?
  • Are there other services serving on the tenant that the specification omits?
  • Is there a MerchIntegrations equivalent we have missed?

How do we manage differentiator group membership, UDA definitions, and initial retail?

Blocked

Three separate things we are currently unable to complete, all foundation-side rather than integration-side.

  • Diff groups. A child colour must belong to the parent's group — BLACK was rejected, 08621 accepted. What is the process for adding a colour to a group: API, or manual setup?
  • UDAs. foundation/uda returns zero rows and itemUda is null on every item. We send an empty array, which succeeds trivially. Is this setup we should be requesting?
  • Initial retail. We can find no write service for it in the tenant specification. Does one exist under a path we have not found?
Tier 4

Platform and operational

Lower stakes individually, but several affect whether we can run this unattended.

Automated token acquisition, and the batch window

Two things standing between us and unattended operation.

  • Tokens. We currently paste an hourly bearer token in by hand. We have MFCS_TOKEN_URL, a client id and a secret reference configured but have not completed the client-credentials flow. What is the correct grant, scope and rotation policy? Any rate limit on token issuance?
  • Batch window. Writes fail with HTTP 400 and the body "Batch Running Indicator is ON". What is the schedule, is it queryable so we can defer rather than fail, and does it differ per environment?

Field naming, unknown parameters, and idempotency

  • Three vocabularies. The feed says originCountryId / physicalQuantityOrdered; writes want originCountry / quantityOrdered; itemDetail says classAttribute, itemDesc, primarySuppInd. Is there a canonical mapping document?
  • Unknown query parameters are silently ignored. dept instead of deptId returns an unfiltered feed that looks filtered. Is rejecting unknown parameters on the roadmap?
  • Idempotency. Is there a native idempotency-key mechanism? We built request hashing ourselves and it may be redundant.
  • Recovery. After a transport failure we resolve the outcome through the operation-status service by correlation id. Is that the sanctioned pattern?
  • Limits. Rate limits, concurrent request ceilings, maximum collection sizes per call, payload size caps?
